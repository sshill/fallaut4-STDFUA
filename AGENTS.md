# Fallout Stand: Правила взаємодії та виконання завдань

## 1. Протокол узгодження: Саммарі діагностики -> Саммарі змін -> Єдине підтвердження
Коли користувач повідомляє про проблему, баг або ставить нове завдання, агент зобов'язаний діяти за чітким двоетапним протоколом:

### Етап 1: Саммарі діагностики (Diagnosis Summary)
- Що саме сталося, які симптоми та точна причина збою.
- Результати перевірки логів та системного стану.
- Короткі, чіткі висновки без води.

### Етап 2: Саммарі пакету змін (Package Summary)
- Чітка таблиця або список усіх файлів, які будуть змінені або створені.
- Список конкретних дій та налаштувань.
- Очікуваний результат після застосування пакету.
- Запит **ОДНОГО** загального підтвердження від користувача на весь пакет.

---

## 2. Пакетне виконання без клікання на кожній команді (Batch Execution)
- **Ніяких покрокових запитів**: Користувач не повинен підтверджувати кожну команду окремо.
- Після того, як користувач підтвердив пакет змін, агент:
  1. Використовує внутрішні інструменти редагування файлів (`replace_file_content`) та стандартний пісочний режим (`BypassSandbox: false`), які виконуються **автоматично без запиту дозволів**.
  2. Якщо потрібні системні команди хоста (що потребують дозволу `BypassSandbox: true`), агент **об'єднує їх в один зведений скрипт або єдиний пакетний виклик**, щоб користувач натиснув «Дозволити» рівно **1 раз**.
  3. Після виконання одразу видає фінальний короткий звіт про результат (Walkthrough).

---

## 3. Мова та стиль відповідей
- Відповіді надаються виключно українською мовою.
- Структурований, спокійний, технічно вивірений тон.
- Клікні посилання на файли у форматі `file://`.

## 4. Обов'язкова процедура інспекції екрана гри через Git (Screen Inspection via Git Protocol)
- **Категорична заборона прямого виклику скріншотера в пісочниці:**  
  Агентам **суворо заборонено** викликати графічні утиліти зняття екрана (`xfce4-screenshooter`, `import` тощо) у стандартному режимі пісочниці (`BypassSandbox: false`). Пісочниця ізолює сокети X11 (`/tmp/.X11-unix/`), що призводить до дедлоків, підвисань або мовчазних збоїв.
- **Обов'язковий триетапний протокол аналізу екрана:**  
  1. 💾 **Збереження кадру на диск хоста:** Кадр робочого столу або вікна гри знімається утилітою хоста і зберігається безпосередньо у файл [`screens/latest.png`](file:///home/hills/Documents/fallaut/screens/latest.png).
  2. 🔏 **Локальна фіксація в Git (Git-First Local Access):** Збережений знімок негайно додається до локального репозиторію та фіксується автономним локальним комітом:  
     `git -C /home/hills/Documents/fallaut add -f screens/latest.png && git -C /home/hills/Documents/fallaut commit -m "feat(screen): <опис контексту> [verified: antigravity]"`
  3. 👁️ **Внутрішній мультимодальний перегляд:** Агент читає збережений та зафіксований файл виключно через внутрішній інструмент `view_file` (`screens/latest.png`). Це гарантує прозору історію всіх переглянутих екранів у Git та 100% захист від збоїв відображення.
- **Стандартизований виконуваний раннер стенда:**  
  Для виконання цієї процедури агенти зобов'язані використовувати єдиний стабільний скрипт стенда:  
  `bash /home/hills/Documents/fallaut/capture_screen_to_git.sh "<причина або контекст знімка>"`  
  *(Скрипт автономно виконує зняття, валідацію, додавання та локальний коміт).*
