# Antigravity Workspace Execution Policy (3-Фазне Дослідження)

## Регламент роботи: 3 фази обробки завдань

Для всіх запитів гравця щодо дослідження, налаштування або модифікації скриптів/системи Fallout 4 суворо дотримуватися 3-фазного процесу:

### Фаза 1: Дослідження та діагностика (Research & Diagnosis)
- Автономне дослідження проблеми, перевірка стану системи, читання конфігурацій, файлів і логів (`Papyrus.0.log`, скрипти, `Fallout4.esm` тощо).
- **Правило щодо команд:** НЕ запитувати підтвердження на окремі діагностичні та дослідницькі команди. Агент виконує їх самостійно.
- На цьому етапі суворо заборонено змінювати бойові файли гри чи системні налаштування.

### Фаза 2: План рішень та гейт підтвердження (Plan & Approval Gate)
- Формування структурованого репорту з пакетом запланованих змін:
  1. Причина проблеми або мета завдання.
  2. Повний пакет змін (перелік файлів, команд та налаштувань, які планується застосувати).
  3. План перевірки функціоналу.
- **Approval Gate:** Зупинка виконання для отримання схвалення користувача («+» або явна згода). Без згоди не переходити до модифікацій.

### Фаза 3: Виконання та верифікація (Execution & Verification)
- Застосування узгодженого пакета дій.
- Звіт про статус кожного зміненого об'єкта.
- Тестування працездатності та фінальний чек-лист перевірки (Verification Checklist).

## Інженерний регламент: Робота з Wine та компілятором Caprica

### 1. Пре-флайт перевірка сигнатур API (Pre-flight API Verification)
- Перед написанням або модифікацією викликів у скриптах Papyrus (особливо нативних методів рушія на кшталт `RemoveAllItems`, `MoveTo`, `FadeOutGame`, подій `OnActivate` тощо) **обов'язково перевірити точну кількість параметрів та їхні типи** у ванільних дефініціях:
  `/home/hills/Documents/fallaut/cache/base_scripts/<ScriptName>.psc`.
- **Суворо заборонено писати виклики API за пам'яттю з минулих ігор** (наприклад, плутати 3-параметричний `RemoveAllItems` зі Skyrim із 2-параметричним у Fallout 4).

### 2. Стандарт виклику компілятора Caprica через Wine
- Компіляція через Wine обов'язково повинна використовувати захищені змінні оточення:
  ```python
  env["WINEDEBUG"] = "-all"
  env["WINEDLLOVERRIDES"] = "winedbg.exe=d;winemenubuilder.exe=d"
  ```
- Це повністю унеможливлює зависання Wine при необроблених винятках компілятора та виключає запуск інтерактивного дебагера `winedbg`.

### 3. Протокол реакції на збої компіляції (Compiler Failure Protocol)
- Якщо `Caprica.exe` падає з кодом помилки або завершується без вказівки номера рядка:
  1. **Крок 1 (Аудит дифу):** Негайно перевірити щойно доданий `git diff` або нові функції на точну відповідність параметрів дефініціям у `cache/base_scripts/`.
  2. **Крок 2 (Заборона сліпої бісекції):** Забороняється запускати тривалі цикли ручного почергового коментування функцій і бісекції без попереднього аудиту сигнатур викликів за еталонними `.psc`.
  3. **Крок 3 (Очищення процесів):** У разі підвисання або збою Wine обов'язково виконувати скидання сесії сервера через `wineserver -k` перед наступним запуском.

## Регламент взаємодії з локальною Ollama (Strict Code-Only Contract)

1. **Профільне призначення:**
   - Модель `qwen2.5-coder` є суто **кодовим інструментом** (синтаксис, структури, функції, регулярні вирази, FIM).
   - **Категорично заборонено** надсилати в Ollama загальні запитання про лор гри, сюжетні факти чи абстрактну логіку (це зона відповідальності хмарного агента).
   - Заборонено оцінювати працездатність Ollama за допомогою «тестових чат-запитань».

2. **Обов'язкові сценарії делегування (Whitelisted Tasks):**
   - Генерація окремих функцій Papyrus за наданою сигнатурою.
   - Створення шаблонного коду (меню, списки FormID, валідація умов).
   - Рефакторинг та оптимізація окремих функцій Python.
   - Точкові перевірки синтаксису.

3. **Вхідні параметри виклику:**
   - Запит передається через `http://127.0.0.1:11434/api/generate` без історії діалогу (`Stateless`).
   - Жорстке обмеження токенів: `num_predict: 250..400`, `temperature: 0.2`.

## Стандарт запуску діагностичних команд (Мінімізація модальних вікон)

1. **Причина появи запитів підтвердження в IDE:**
   - Модальне вікно виникає, коли команда запускається з прапорцем `BypassSandbox: true` (доступ до X11/GUI/Wine поза пісочницею) або коли кожен скрипт має унікальне ім'я (ламає правило префіксного автосхвалення «Always Allow»).
2. **Інженерні правила для безперервної діагностики:**
   - **Стабільні імена утиліт:** Для інспекції гри використовувати стабільний файл-раннер (наприклад, `python3 /home/hills/Documents/fallaut/game_console_copilot.py ...` або єдиний `scratch/diagnostic_runner.py`), а не генерувати десятки тимчасових скриптів (`click_guy_umbrella.py`, `pageup_console2.py`), на кожен з яких IDE вимагає нове схвалення.
   - **Пріоритет пісочниці для читання:** Читання файлів, пошук FormID у `.esm`, парсинг логів і коду виконувати виключно в стандартному режимі (`BypassSandbox: false`), який виконується миттєво і повністю автоматично.
